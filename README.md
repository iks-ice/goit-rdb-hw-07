# goit-rdb-hw-07

**Домашня робота №7: Time Series та JSONB у задачах ML**

## Джерело даних

NYC TLC Yellow Taxi Trip Records: https://www.nyc.gov/site/tlc/about/tlc-trip-record-data.page

Notebook завантажує офіційний файл `yellow_tripdata_2024-03.parquet` (до 500 000 перших записів), очищає аномальні `fare_amount` та `trip_distance` і створює щоденні агрегати. Якщо файл недоступний, використовується **stub-schema fallback**: 60 днів × 5 зон = 300 рядків. Реальний і stub-режими позначаються у виводі notebook.

## Як запустити

1. Завантажити `goit_rdb_hw_07_taxi_jsonb.ipynb` у Google Colab.
2. Обрати **Runtime → Restart session and run all**.
3. Перевірити кількість рядків `t7_hw_taxi_daily`, таблицю `t7_hw_events` і результати `EXPLAIN (ANALYZE, BUFFERS)`.
4. Замінити позначені місця у Reflection фактичними значеннями планів.
5. Зберегти notebook з output перед здачею.

## Архітектура

- `nyc_taxi_raw`: тимчасовий raw-шар для реального NYC Taxi.
- `t7_hw_taxi_daily`: денний агрегат за `pickup_zone_id` та `ts_day`.
- `v_t7_hw_taxi_calendar`: calendar spine для відсутніх дат.
- `v_t7_hw_taxi_features`: lag 1/7/30 днів, rolling 7-day average fare, rolling 30-day standard deviation, cumulative trips та expanding average.
- `t7_hw_events`: 50 000 синтетичних подій п'яти типів з різними JSONB payload.
- GIN `jsonb_path_ops` для containment `@>` та expression B-tree для `payload ->> 'device'`.
- `t7_hw_checkouts_norm`: типізована checkout-таблиця для порівняння з JSONB.

## Часові типи

Денні агрегати рахуються за локальним календарним днем Нью-Йорка (`DATE`). У режимі реального NYC Taxi демонстраційна таблиця зберігає pickup/dropoff як `TIMESTAMPTZ` через `AT TIME ZONE 'America/New_York'`.

## Обмеження

Фактичні плани та швидкодія індексів залежать від обсягу даних і середовища. `EXPLAIN`-виводи з'являються лише після запуску в Colab. Stub-схема є навчальною альтернативою, а не реальними даними TLC.

## Рефлексія

У цій роботі я дослідив побудову часових ML-ознак і зберігання подій із різними схемами у PostgreSQL. Для NYC Taxi я сформував щоденні агрегати, лаги, ковзні статистики та накопичувальні показники. Окремо врахував відсутні дні через calendar spine, оскільки без нього LAG(..., 7) означає сім попередніх рядків, а не обов'язково сім календарних днів.

Для JSONB-подій я порівняв плани виконання containment-запиту до та після створення GIN-індексу. До індексації план містив [оператор], загальний cost становив [значення], а час виконання [значення] мс. Після індексації я побачив [оператор], cost [значення], час [значення] мс. Якщо PostgreSQL залишив Seq Scan, це може пояснюватися селективністю умови або тим, що послідовне читання невеликої таблиці дешевше.

GIN jsonb_path_ops корисний для @> containment, оскільки індексує структуру та значення JSONB для відповідних пошукових операцій. Однак для payload ->> 'device' = 'mobile' доцільніший expression B-tree index: він індексує саме текстове значення конкретного шляху. Після створення індексу я отримав [оператор, час]. Індекси зменшують вартість вибіркового читання, але збільшують витрати на INSERT, UPDATE, дисковий простір і обслуговування.

JSONB я обрав би для подій із мінливими payload-схемами, де нові поля з'являються часто. Нормалізовані таблиці краще підходять для стабільних критичних атрибутів із перевірками типів, обмеженнями та частими аналітичними запитами. Порівняння checkout-агрегацій показало [фактичні оператори й час двох планів].

Новий тип refund у JSONB-підході можна додати без зміни структури таблиці, передаючи новий event_type та відповідний payload. У нормалізованому підході я створив би окрему таблицю повернень із типізованими колонками, ключами та constraints, а також міграцію і завантаження історичних записів. Головний компроміс полягає у гнучкості схеми проти гарантій цілісності й вартості запитів.
